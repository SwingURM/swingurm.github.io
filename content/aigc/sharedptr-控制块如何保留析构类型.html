SharedPtr 控制块如何保留析构类型

非虚析构函数与基类子对象

既然删除器调用的是 Derived 的析构函数，而 Base 的析构函数又不是虚函数，Derived 中的 Base 子对象会不会漏掉？不会。C++ 工作草案的 class.dtor 规定：析构函数体执行完毕后，会自动析构该类的非静态成员、非虚直接基类；如果当前类是最派生类，还会析构虚基类。基类和成员按构造完成顺序的逆序析构。

析构函数体与子对象的销毁

需要区分析构函数体和整个对象的析构过程：~Derived() { ... } 中花括号里的语句只是用户编写的函数体。执行完函数体后，语言规则还会自动销毁成员和基类子对象；这部分并不需要写进花括号。对于类类型的成员，销毁它会调用该成员类型的析构函数，并递归地销毁它自己的成员和基类。

再区分析构对象和释放对象占用的存储空间：对这个由普通 new Derived 创建的对象执行 delete，既会进行上述析构，也会调用释放函数归还存储空间。单独显式调用 p->~Derived() 会进行对象和子对象的析构，却不会自动归还 new 分配的存储空间；这种写法用于手动管理生命周期，不能再对同一对象直接 delete，否则会重复析构。原项目中 SharedPtr<Base> p(new Derived) 的默认删除器使用的是对 Derived* 的 delete，因此完成这两件事。

虚析构函数关系到通过基类指针删除派生对象时能否正确处理动态类型，不决定进入 ~Derived() 后是否析构基类子对象。工作草案 expr.delete 规定，对于普通的单对象 delete，当静态类型与动态类型不同时，通常要求静态类型是具有虚析构函数的基类，否则行为未定义；该规则对 destroying operator delete 有例外。

传入指针的静态类型

类型推导依据的是传给构造函数的表达式的静态类型，并不是运行时自动探测对象的动态类型：

这里控制块使用 DefaultDeleter<Base>，即通过 Base* 执行 delete。如果 Base 的析构函数是虚函数，会通过虚析构调用到 Derived 的析构函数；如果它不是虚函数，那么在通常的删除方式下通过这个 Base* 删除 Derived 对象是未定义行为。控制块不能从 Base* 推导回原来的 Derived*。

上面的结论针对默认删除器。构造时也可以传入自定义删除器，此时控制块保存该删除器，最终如何处理对象由它决定。自定义删除器需要与实际资源及其生命周期相匹配。

控制块不仅决定如何销毁对象，也决定何时销毁对象。一个常见问题是：shared_ptr 不保护被管理对象的并发读写，那引用计数为什么不全部使用 memory_order_relaxed？

这是 ISO C++ 邮件讨论中提出的措辞思路，不是这里引用的标准现有条款；该讨论建议向 LWG 确认标准文字是否已经充分表达这一预期。下面先把它当作设计目标，以理解为什么实现需要同步。reset()、赋值等也可能释放所有权；完整规范需要覆盖这些路径，不能直接把上面的析构措辞视作完整标准表述。

在这个假设下，通过 happens-before 的传递性，A 的访问先于最终删除器。我们需要实现的跨线程关系正是中间这一环：只让计数原子地增减，无法自动建立它。同时，这个目标不保证持有者之间的普通并发读写互相有序。

从一个析构读取成员的例子思考

假设 A 的 reset() 先将计数从 2 减到 1，B 的 reset() 再将其从 1 减到 0，并在 B 中执行析构函数。为了让 A 对 x 的写入与 B 的析构读取不构成数据竞争，需要建立 A 写 x happens-before B 析构时读 x。如果 B 先释放，则 A 自己最后释放并析构，写入与析构处于同一线程。

仅有计数的原子修改顺序不够：即便 B 的原子减一读取了 A 写出的计数值，两个操作若都为 relaxed，它们本身也不建立跨线程的 synchronizes-with。这是针对这种具体原子计数实现的分析；标准对 shared_ptr 的措辞和实现方式的关系见下文。

怎样判断是否需要同步

单看“内存操作能否跨过引用计数修改”容易混淆抽象机的顺序与硬件重排。可以先画三个关系：

  1. 找冲突操作：例如一个线程写对象成员，另一个线程的析构函数读取同一成员。
  2. 画线程内顺序：同一线程中，对象访问 sequenced-before 后续的 reset()；即使计数操作是 relaxed，已有的 sequenced-before 仍然成立。
  3. 找跨线程同步边：若最后的析构发生在另一个线程，还需要某种同步将两侧连起来。单纯的 relaxed 计数修改顺序不是这样的同步边。

所有权不是对象读写锁

两个线程分别持有 shared_ptr，不能因此并发写入同一个普通 int 成员；之后的引用释放不会倒过来消除数据竞争。不同线程同时操作同一个 shared_ptr 实例且至少一方修改它，也需要同步；不同的 shared_ptr 实例可以共享所有权并独立操作。

use_count() 同样不是同步协议。工作草案对它注明 “Synchronization: None”，并指出 use_count() == 1 不意味着此前通过已销毁的 shared_ptr 进行的访问已经完成。更强的原子顺序也不能让一个已经销毁的控制块复活；不能从不受保护的裸控制块指针安全地直接加引用。

标准措辞与实现：邮件讨论的边界

C++ 工作草案明确描述了共享所有权和最后所有者负责销毁资源；析构条款描述了何时调用删除器或 delete。但不能把“所有持有者释放前的访问 happens-before 最终销毁”当作这些条款中直接写出的原文。

在 2025 年的 ISO C++ std-discussion 讨论中，发帖者质疑标准是否明确规定了这样的顺序。后续讨论以类似上面的 Wobble 例子说明问题，并提出用其他共享所有者的释放与最终删除器调用之间的先行关系来表达预期；讨论后段认可 release/acquire 等实现思路，并建议提交 LWG issue。邮件是参与者的分析和提议，并非委员会正式裁定；此处未确认后续 issue 或裁决。标准规定可观察行为，不要求所有实现使用某一种具体内存序。
